## 1. 环境前置与执行顺序

由 DBA 提供可丢弃的测试实例、支持当前脚本的 SQL Server 版本、创建测试库的权限及独立会话。记录完整 `@@VERSION`、兼容级别、排序规则、DBCC USEROPTIONS、采集时间与脚本 hash；不将开发机 SDK 或 XML Build 属性写成数据库实际版本。

1. 在独立测试实例运行 [00-PrepareIsolatedDatabase.sql](./sql/00-PrepareIsolatedDatabase.sql)。它只创建命名为 `SqlXmlAnalyzer_Imp02_Acceptance` 的新库；若同名库已存在则报错，不复用旧库。单批次保护检查避免跨 GO 之后继续执行初始化。
2. 新库具有 `SqlXmlAnalyzer.IMP02=SyntheticAcceptanceFixture-v1` 所有权标记。后续脚本在该库执行并检查标记；测试数据仅含人工账号和整数。
3. 在新的查询会话运行 [10-SemanticCounterexamples.sql](./sql/10-SemanticCounterexamples.sql)，保存所有结果集与元数据。该脚本演示参考反例，不自动运行当前引擎生成的候选 SQL。
4. 核对本次运行 `candidates/R02.sql`、`R19.sql`、`R20.sql` 的 hash 和内容；在测试库的新会话分别执行原 SQL 与候选，保存各自结果、错误码、事务状态和对象副作用。不要在生产库或有未提交事务的会话中执行。
5. 按下节采集实际计划和死锁；不满足形态要求的输入记录真实形态，不强行标为并行/循环样本。
6. 保存结果后关闭测试会话，执行 [90-CleanupFixtureObjects.sql](./sql/90-CleanupFixtureObjects.sql)。只删除本准备脚本创建的四张表及标记，保留测试库供审阅。移除整个库需另行核对数据库名称和保留资料，不在此脚本自动执行。

中途失败时，先在当前测试会话检查 `@@TRANCOUNT`，回滚该会话未完成的测试事务并关闭会话，使本地临时对象释放；再检查库和所有权标记。00 若只创建了库但初始化失败，不直接重跑或覆盖它；先检查失败阶段。清理不会撤销外部采集器配置，若 DBA 新建了 XE 会话，应在采集记录中列出停止/删除该测试会话的步骤。

## 3. 实际计划与死锁采集

运行 [20-CaptureActualPlans.sql](./sql/20-CaptureActualPlans.sql)，按服务器实际返回保存 XML 原件。文件和批处理/语句对应关系保持可追溯；服务器若返回多个独立 XML，就保存多个文件及其顺序，不能手工拼接后宣称它是原始采集文档。

- 串行：检查实际计划中的线程和算子，再标记串行能力。
- 并行：MAXDOP 4 仅允许并行，并不保证选择并行；若实际仍串行，本次并行夹具需求仍未满足，应由 DBA 调整测试数据/查询并记录调整。
- 循环：检查被重复执行算子的实际执行次数；LOOP JOIN 提示不等于每个目标算子一定执行多次。
- 估算/实际：分别保存，记录具备的指标，缺失字段不能补 0。
- 多语句：保留同一采集批次和原始语句身份，用于 R16；不得依赖 NodeId 在整个文件中唯一。

测试死锁使用 [会话 A](./sql/30-DeadlockSessionA.sql)和[会话 B](./sql/31-DeadlockSessionB.sql)，在两个测试会话的等待窗口内启动。若没有发生死锁或只发生锁超时，记录真实结果，不声称已取得死锁夹具。由 DBA 通过实例上适当的 `xml_deadlock_report` 采集机制保存原始事件 XML / XEL、事件时间和来源；本包没有自动启用或修改任何 XE 会话。

真实采集结果使用 [fixture-record-template.json](./fixture-record-template.json) 建立元数据。审查隐私后生成可共享副本，并分别记录原件/副本 hash、修改字段和仍保留的敏感范围。没有可靠采集来源或缺少元数据的仓库样例仍保持 provenance unverified。
